# SDD 升级：已有约定的条款对齐与形态变更

## 这份 skill 改的是**已经存在的东西**

| | sdd-init | sdd-upgrade（本 skill） | sdd-interview |
|---|---|---|---|
| 前提 | 没有状态文件（冷启动） | 有状态文件，且 `sdd-loop check` 是绿的 | 结构已在 |
| 核心动作 | 建：从无到有落模板 | **改**：定向补条款、挪目录 | 产内容：四份阶段文档 |
| 安全规则 | **不覆盖已存在的东西** | **不删用户的东西，动手前留退路** | 不替人确认 |

**为什么不是 sdd-init 的一个分支**：init 的承重规则是「不覆盖已存在的东西」，而升级的动作恰恰是「改已存在的东西」。塞进一份 skill，两条规则会互相打架，而打输的会是安全的那条。

## 五类动作，可以只做一类

1. **条款对齐**（低风险，任何老仓库都该做一次）：本包往模板里加过的门禁条款，老仓库拿不到——`sdd-init` 不覆盖已有的 `AGENTS.md`，所以模板演进对已落地的副本不生效。
2. **形态迁移**（可选）：单流 → 按系统分流。只在真撞上「唯一的活跃 Loop 被一个人占着，别人的活进不了门禁」时才做。
3. **AGENTS 审计与无损精简**（可选，高风险）：生成 Candidate 和逐项分类，只对用户逐项授权的删除、移动或合并落地。
4. **治理 v1 启用**（可选）：给尚未启用治理的仓库加入角色映射、append-only 审计、审批/Continue 停点和四项工程扩展。它改变后续 Loop 的门禁，必须单独展示迁移结果并取得授权。
5. **已关闭 v1 → 后续 v2**（可选）：目标流的 v1 Loop 和独立修复均已关闭后，对齐 v2 规则并切换该流的治理版本；下一项工作才按锁定的 v2 流程启动。进行中的 v1 工作不迁移。

先问用户要做哪些。条款对齐与形态迁移同时做时，**先对齐条款，再迁形态**。AGENTS 审计始终最后做，因为 Candidate 必须基于升级后的 canonical 条款。

动作四启用 v1 治理后，`sdd-loop check` 会执行 v1 的 C6-C10；未启用治理的旧仓库继续只执行原有检查。不得只补 `governanceVersion` 而不补角色、扩展和门禁字段，那会把仓库立刻变红。动作五切到 v2 后，同名 C6-C10 改由 v2 工作流检查，不能把切换后的绿色当作旧 v1 审计已重新验证。

## 动作四：治理 v1 启用

1. 读取当前 Git `user.name` / `user.email`，请用户确认六类角色的邮箱映射；缺身份不编临时值。
2. 在状态文件一次性加入 `governanceVersion: 1`、`gateStage`、`gateState`、`gateFingerprint`、`enabledExtensions` 和六类 `role*` 字段。四项内置扩展必须为 `testing,pbt,security,resiliency`。
3. 补齐 `AGENTS.md.CHANGELOG.md` 中 2026-09-09 的常驻条款；逐条展示后再写，不覆盖项目自有内容。
4. 没有活跃 Loop 时只启用字段，下一 Loop 从 Requirements 完整记录。已有活跃 Loop 时记录一次 `governance_migrated`，写明当前阶段、缺失历史及原因；当前阶段文档若已 confirmed，工具把它绑定指纹并停在 `awaiting-continue`，必须等后续用户消息再推进。已经进入 Implementation 或 Verification 时，还要在 `implementation.md` 记录一次性“治理审计豁免”。豁免不得延续到下一 Loop。
5. 不为不存在的历史对话伪造事件。已有确认文档只记录“迁移时已存在”的事实和当前指纹，不能冒充原确认人重新签字。
6. 重跑 `sdd-loop check`；角色缺失、审计断链、扩展缺证据或指纹失效必须原样报告，不手改 JSONL 绕过。

## 动作五：已关闭 v1 → 后续 v2

这只切换**目标流的下一项工作**，不迁移已有 Loop、Hotfix 或 Debug。单流仓库以唯一状态文件为目标；分流仓库逐流处理，不借项目级 `AGENTS.md` 的更新擅自切换其他流。`sdd-loop workflow start` 会拒绝给已有 v1 `audit/` 的活跃 Loop 建 v2 锁，因此不得通过手改 `governanceVersion` 绕过。

1. **先确认旧工作真正关闭。**在目标流仍为 `governanceVersion: 1` 时运行并保存该流 `sdd-loop check` 的完整结果；确认 `activeLoop: null`、`lastClosedLoop` 指向已归档的 Loop，且没有未关闭的 v1 Hotfix 或 Debug。任一项未满足，保留 v1，先完成旧工作。旧审计与归档文档原样保留，不伪造 v2 `started`、`stage_completed` 或签署事件。
2. **先验证新能力。**运行 `sdd-loop capabilities --require governance@2 --host <当前宿主>`，退出非 0 时停止；排查包资源、宿主 Skill 落点和冲突，不自动安装、覆盖已有 Skill 或切换工具版本。只在能力通过后继续。用 `sdd-loop workflow show --route loop --repo <仓库> [--stream <流>]` 展示下一轮将采用的依赖图；若项目已有流程覆盖，先核对覆盖内容，不把默认流程冒充项目流程。
3. **准备可审阅的候选。**按动作一核对 `AGENTS.md.CHANGELOG.md` 的 2026-09-28 四条 v2 探针，逐条展示要补的原文及位置。先检查目标流和每条兄弟流的 `governanceVersion`：`AGENTS.md` 必须按所属流版本分派新工作，仍为 v1 的兄弟流今后的工作仍走 v1；不得把“新工作默认治理 v2”、固定阶段顺序或 `governance@1` 预检写成跨版本的无条件规则。旧 v1 阶段、审批、角色映射、审计位置、工程扩展、Hotfix 和 Debug 规则必须明确限定为 v1 工作。若现有无条件条款与 v2 冲突，不能只追加一句新规则：把冲突原文、拟修改内容及其对兄弟流的影响列进 Candidate，逐项取得授权；动作五允许按这份已确认的 Candidate 定向改写冲突条款，其他清理仍走动作三。状态候选只针对目标流：`governanceVersion: 1` 改为 `2`，移除只表示 v1 当前门禁的 `gateStage`、`gateState`、`gateFingerprint`（最终旧值已在切换前快照与 Git 历史中）；保留角色映射、归档编号与旧审计。不要改阶段文档正文或其他流的状态。还要检查兄弟 v1 流的已关闭归档是否缺 `deliveryScope`，或有效范围（包括目录范围）是否覆盖根 `AGENTS.md`：两者都可能让本次改动触发旧 C10 漂移；在 Candidate 中列出受影响的流及切换前后指纹判据，先取得单独的漂移核对与接受授权，或改为所有流关闭后一起升级。不得为了本次升级伪造旧审计或缩小真实交付范围。
4. **取得用户对候选的明确确认后落地。**对 AGENTS 条款和目标状态文件只做已展示的修改。切换前后各保存一次 `sdd-loop check --repo <仓库> [--stream <流>]` 结果，并额外执行不带 `--stream` 的全仓检查：C1-C5 的状态与归档事实应一致，切换后的 v2 C6-C10 必须干净；旧 v1 C6-C10 的结果保留为切换前证据，因为 v2 检查不会重判旧审计。兄弟流若出现预告过的旧 C10 漂移，必须按现有 `closure_drift_accepted` 流程由 Approver 核对并明确接受，留下独立证据后再收尾；未经接受就停止并恢复候选前状态。其他新问题同样停止并恢复候选前状态，不改旧 JSONL 来消红。
5. **下一项工作才启动 v2。**在确认新目标后加载 `sdd-route`，先推荐 Loop、Hotfix 或 Debug 并等用户确认具体路线，再用 `workflow start` 固定定义。不要在切换前为下一 Loop 写 v1 审计，也不要把版本切换本身当作新工作的路线确认。

**无论用户只选动作一、只选动作二还是两者都做，只要仓库已经是分流或本次会迁成分流，就必须做「分流状态入口兼容检查」**（动作二第 4 步）：确认 `AGENTS.md` 没有把已经不存在的根状态文件 `docs/loops/status.md` 继续写成入口。它修的是上一版分流规则留下的自相矛盾，不是可选的条款升级。

## 动手之前：四道自己的门禁

这四条一条都不能跳。**它们不是仪式，每一条都对应一种「改到一半没法回头」。**

1. **先验证能力，再看 `sdd-loop check`。** 运行 `sdd-loop capabilities --require governance@1 --host <当前宿主>`（Claude Code=`claude`、Codex/Kimi Code 等共享 Agent Skills 宿主=`agents`、OpenClaw=`openclaw`、Hermes=`hermes`、pi=`pi`）；命令不存在、退出非 0、协议不受支持或宿主未就绪时停止，按 `https://github.com/Roger0808/sdd-loop` 的 README 更新，未经用户明确授权不得自动升级。能力通过后，`sdd-loop check` 必须是绿的。报红就先把矛盾解决掉再来——在一个已经声明与事实不符的仓库上挪目录，改完你分不出新出现的红是搬错了还是本来就红。报「判据读不出来」更要停下：那说明状态文件被污染，你读到的 `activeLoop` 是猜的。旧 CLI 可能忽略治理字段，因此 check 绿色不能替代能力预检。
2. **`git status` 必须干净。** 有未提交改动就先请用户处理。本 skill 会移动文件，混在别人的改动里没法单独回退。
3. **把当前 check 的完整输出存下来**（原样贴进对话或写进临时文件）。这是收尾时逐条比对的基准——没有基准就没有「没搞坏」的证据，只有「看起来还行」。
4. **确认没有别人正在这个仓库里干活。** 迁形态会移动活跃 Loop 目录，别人手上的路径会当场失效。

如果只做动作三，仍要满足前三条；审计可以在只读环境进行，但采用 Candidate 会修改仓库，不能把两者混成一步。

## 动作一：条款对齐

### 1. 读变更记录，不要整份 diff

清单在 `sdd-init` skill 目录下的 `AGENTS.md.CHANGELOG.md`。它按批次列出本包往模板里加过的每一条：条款、在哪一节、**探针**（一小段原话）、为什么加。

**只核这份清单上的条款。** 用户的 `AGENTS.md` 落地之后就是他自己的文件，里面有大量**合法**的自有改动——改过的路径、当初按形态删掉的条款、自己加的内容。拿模板整份 diff 会把这些全报成差异，而噪音一多，人就开始整段跳过：**假警报比漏报更致命**。

做法：拿每条的探针去用户的 `AGENTS.md` 里搜。搜得到 → 已经有了，跳过。搜不到 → 候选。

### 2. 判断这一条该不该补

搜不到**不等于**该补。先判它属于哪一档（变更记录里写着）：

- **常驻条款** → 该补。任何项目都要有。
- **多人档 / 分流档** → 先看这个仓库是不是那个形态。单人独占的仓库不需要「确认人的决定权」；仍是单流的仓库不需要「归档按流分」。**不适用的不要补**——补进去只会让规则说的和仓库的实际形态对不上。

拿不准这个仓库是什么形态，就问用户（判据见 `sdd-init` 第 2 步那两问：范围能不能互不重叠地切分，不是几个人）。

Debug 条款还有一项启用前提：若状态文件没有 `governanceVersion: 1` 或 `roleApprover`，条款对齐仍可把完整的 Debug 规则补进 `AGENTS.md`，但必须同时明确报告“规则已对齐、通道尚未启用”，并在条款里保留“开始修复前先走治理升级”的 fail-fast 原文。用户没有选择动作四时不得顺手启用治理，也不得宣称 `/sdd-debug` 已可收口；用户选择动作四后，按治理升级步骤补齐字段和角色再报告可用。

审查者选择条款有一个互斥检查：若旧 `AGENTS.md` 仍允许“同一 Agent 清理实施上下文后审查”或等价自审降级，不得只追加“当前 Agent 本体不得自审”使两条规则并存。先展示冲突，暂停动作一；用户选择动作三后，在 Candidate 中逐项标明旧规则删除和新规则加入，只有获得该条明确授权才采用。未授权时保留旧文件并报告这项门禁未升级，不声称审查隔离已生效。

同样地，2026-09-28 的新探针缺失时先找旧的“新工作默认治理 v2”和无条件 v1 固定阶段、`governance@1` 预检条款。若这些条款仍在，动作一不得直接追加新版措辞；已关闭 v1 流选择动作五，在 Candidate 中定向改写，其他情况选择动作三逐项授权或保持原状并报告冲突。

### 3. 摆出来，等用户点头再动手

把候选逐条摆给用户：**这一条是什么、为什么当初加它、放进哪一节**。用户点头才写。

- **逐字复制模板里的原话**，不要改写、不要"结合本项目优化措辞"。改写会让仓库声明的规则和 `sdd-loop` 的判据对不上，检查就成了摆设。
- 插进对应的节，**保持用户原有的条款顺序和自有内容**，不重排、不"顺手整理"。
- **一个字都不许删。** 你在这一步唯一被允许的动作是「加」。用户 `AGENTS.md` 里有你觉得该改的东西，摆出来说，由他决定。

## 动作二：形态迁移（单流 → 分流）

### 1. 先定流的划分

一条流 = 一个能各自独立交付的子系统，**流名就是目录名，也就是它的范围**。先勘察（workspaces / packages / apps / services / systems 这类结构），把候选摆给用户，由用户定。不要自己决定切几条。

### 2. 只安置现在有的那条，别的按需长出来

**迁移不需要一次建七条流。** 只把**现有的那条**安置好，其余的谁要开 Loop 谁建自己的 `status.md`（那是访谈第 0 站的活）。空的流目录进不了 git，建了也是空转。

问用户一句：现在这条活跃的 Loop 属于哪条流？答案就是它要搬进去的目录名。

### 3. 搬，全程 `git mv`

设主流名为 `<S>`，用户的路径以 `AGENTS.md` 和 check 输出里的实际值为准（下面写的是默认布局）：

- `docs/loops/status.md` → `docs/loops/<S>/status.md`
- `docs/loops/loop-N/` → `docs/loops/<S>/loop-N/`（每一个都搬，不只是活跃那个）
- `docs/archive/loop-N-*/` → `docs/archive/<S>/loop-N-*/`（已归档的也要归位）

四条规矩：

- **一律 `git mv`**，不要 `cp` + `rm`。历史断了，以后没人能追溯这份需求是什么时候确认的。
- **`activeLoop` 的值不动。** 迁移不是关 Loop，编号原样保留（它现在是流内编号，恰好还是原来那个数）。`lastClosedLoop`、`nextLoop` 同理。
- **归档必须跟着按流分。**这不是整齐，是判据：`check` 拿 `loop-` + `lastClosedLoop` 当前缀去归档根里扫，多条流共用一个归档根时，A 流声明 `lastClosedLoop: 1` 会扫到 B 流的 `loop-1-*`，然后去校验**别人**的文档——错误归属，成片假警报。
- **不删任何东西。** 搬完发现有对不上的（多出来的目录、认不出的文件），摆给用户，不要自行处置。

### 4. 顺手要改的三处

- **`docs/backlog.md`**（如果有）：每条补上归属——某条流，或者「跨流」。分不出归谁的摆给用户，不要猜。
- **`AGENTS.md`（分流状态入口兼容检查）**：两件事，缺一件都会留下一份自相矛盾的门禁。
  1. **补**分流那一档的条款（走动作一的流程，探针在变更记录里）。
  2. **替换**写死了根状态文件路径的那些句子。老仓库里的原话通常是「项目当前状态只维护在 `docs/loops/status.md`」和「关闭 Loop 时…更新 `docs/loops/status.md`」。分流之后根目录下没有这个文件，这两句和新补进去的「状态每条流一份」**直接打架**——同一份门禁声明了两个状态入口，读它的人不知道该信哪个。改法照当前模板：常驻那句不带路径（「先读状态文件」「更新状态文件」），路径只出现在分流那一段里。
     这是动作二被允许改写用户已有条款的唯一情形，理由是不改就留下矛盾；照例摆给用户看过再动手，逐句点名「旧写法 → 新写法」。**范围仅限这两句**，别的条款一个字都不动。动作五另允许在 Candidate 逐项授权后定向改写 v1/v2 冲突条款。
     已经是分流、只是来做条款对齐的仓库同样要看这一处——它是上一版迁移留下的欠账。
- **正文里裸写的「Loop N」**：分流之后跨流引用会有歧义，可以改成 `<S>/loop-N`。**但范围只到非阶段文档**：`AGENTS.md`、`CLAUDE.md`、`docs/backlog.md`、README 这类。这一条只管 **Loop 编号**——条款编号（REQ-001、BND-002）不动，它们只在同一条流的文档族内部互相引用。

**阶段文档（requirements / architecture / specification / tasks / implementation / verification，含归档里的）里的「Loop N」默认不改。**它们是确认过的判据：只改正文而保留旧的 `confirmed`，正是用户自己的 `AGENTS.md` 里明令禁止的那件事（「不得只改正文而保留旧确认状态」）。而且歧义其实不存在——流内文档里的「Loop 3」指的就是本流的 Loop 3。

真要改，那是一次**独立的、要用户点头的**动作，不能混在迁移里：逐处摆出来（文件 + 原句 + 改成什么）→ 说清影响（这份文档被谁引用）→ 用户点头 → 按该仓库的确认留痕规则重新留痕。这三步缺一步就不许动。**静默改一份 confirmed 的阶段文档，是本 skill 最不能犯的错。**

### 5. 建立 worktree 规则的过渡

分流后的新 Loop 一律在独立分支和 worktree 开始，主工作区只做同步、集成和审查。分支命名优先沿用项目现有约定；没有时用 `<host-prefix>/<stream>-loop-<n>`。

如果升级时当前 Loop 已在主工作区进入 Implementation，不强行中途搬迁。在当前 `implementation.md` 记录“worktree 豁免”、原因、当前分支和只对本 Loop 有效；下一 Loop 不得继承。尚未进入 Implementation 的 Loop 不得使用这个豁免。

## 动作三：AGENTS 审计与无损精简

读 `sdd-init` skill 目录下的 `AGENTS.md.AUDIT.md`，按它的八分类和四结论执行。

1. 先在 `/tmp/sdd-loop-agents-<repo>-<timestamp>/` 备份当前 `AGENTS.md`，生成 `AGENTS.candidate.md` 和逐项报告。
2. 每个原指令单元恰好分类一次。`UNCLEAR` 保留并询问；不能把模糊或相互冲突的规则自动消解。
3. Candidate 不得直接覆盖。删除、移动、合并逐项摆给用户，只落地获得明确单项授权的部分。
4. 不修改 `.claude/`、`.codex/`、`.agents/`、模型、权限、MCP 或宿主配置。
5. 采用后重跑 `sdd-loop check`，比较行数/字节数/删除和迁移项，只输出一个审计结论。

## 收尾验证

1. **重跑 `sdd-loop check`**（不带 `--stream`，让它自己发现有几条流）。
2. **和动手前存的那份基准逐条比**：条款对齐与形态迁移时，C1/C2/C3/C5 的结论、当前门禁、下一步的 Loop 编号与阶段状态都应该一一对得上，只是路径可能多一层流名。**多出来任何一条新的不一致，就是搬错了**——回去找，不要接受「大概是因为分流了吧」这种解释。动作五还须展示目标流切换前的 v1 C6-C10 与切换后的 v2 C6-C10，解释两者判据不同；其他流的门禁结论不得因本次切换变化。唯一可能的旧 C10 漂移须已在 Candidate 中预告，并有 Approver 的独立核对与 `closure_drift_accepted` 证据，不能当作升级自动豁免。
3. **报告写四件事**：改了哪几个文件（逐个点名路径）；补了哪几条条款（逐条点名，以及属于哪一档）；搬了哪些目录（旧路径 → 新路径）；check 前后的对照结果。
4. **摆出没做的部分**：变更记录里因为形态不适用而没补的条款，列出来说明为什么没补——用户以后转形态时要知道还欠着哪些。

## 明确不做

- **不动业务内容。** 阶段文档的正文一个字都不改（含裸写的「Loop N」——要改走动作二第 4 步那三步，用户点头 + 说清影响 + 重新留痕）。动作四和动作五只按各自列明的治理字段定向修改状态文件；要改业务内容去 `sdd-interview`。
- **不替用户确认。** 迁移不改任何文档的确认状态。
- **不删任何文件或目录**，包括你认为是残留的。只报，由用户决定。
- **不解决 check 报出来的矛盾。** 那是人的活——而且动手前 check 就该是绿的。
- **不重排、不精简用户已有的条款。**动作一只加不改，一个字都不删；动作二只允许改写两句失效的根状态入口；动作五只允许按已确认 Candidate 定向改写与 v2 冲突的旧门禁。其他删除、移动、合并只能在用户明确选择动作三并逐项授权后进行。
- **不碰别的仓库。** 一次只升一个。
