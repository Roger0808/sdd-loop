# SDD 访谈：从一句话到四份文档

## 这份 skill 是什么、不是什么

访谈产出直接写进 Loop 目录里的阶段文档，`status: draft` 起步。确认是人的动作，skill 不代办；但治理模式下必须通过审计事件留下原始意图、答案、审批和后续 Continue，不能只留一句无法追溯的 `confirmed`。

配套的两件仪器（sdd-loop 包提供，不属于本 skill）：

- `sdd-loop check`：每轮开局读状态。本 skill 不管状态对账。
- `sdd-loop guide --type <文档>.<条款>`：**写任何条款之前**先查口径和本仓现有编号族。例：`sdd-loop guide --type specification.entity-table`。

## 治理模式：先记录，审批后停下

状态文件含 `governanceVersion: 1` 时：

1. 创建活跃 Loop 和 requirements.md 后，把用户最初的需求原文作为 `intent_captured` 事件记录；疑似凭据由工具脱敏，不要先复制进别的文件。
2. 每轮关键回答记录 `question_answered`；只记用户答案与决策摘要，不保存完整 AI 输出。
3. 每个阶段开始时读取 `sdd-init/references/extensions/README.md`，只加载本阶段需要的内置规则和已启用项目扩展。Requirements 只读自定义 `.opt-in.md`，答案决定是否把扩展名追加进 `enabledExtensions`。
4. 用户确认阶段文档后，将文档标为 `confirmed`，用临时 JSON 调 `sdd-loop _governance record` 写 `stage_approved`。工具进入 `awaiting-continue` 后，**立即结束当前响应**。
5. 只有用户后续消息明确要求继续，才写 `continue_authorized`。同一条消息里的“批准并继续”只执行批准，不能跨越停点。

事件 JSON 至少含 `type`、`role`、`stage`、`summary`；原始答案放 `input`。临时文件不得提交，调用结束后删除。Git 身份缺失、角色不匹配或指纹变化时停止，不手改审计来绕过。

## 总原则：SDD 文档 = 抽取（访谈）+ 勘察（读代码/环境）+ 现场沟通

访谈只能得到用户脑子里的东西。代码现状、接口错误语义、运行环境，用户要么不知道、要么说的是印象。凡是依赖代码现状的内容，**必须去勘察**（读代码、读配置、跑只读命令）；勘察不到就在文档里标「待勘察」。

**抽不出来要明说，不许编。** 编出来的架构结论会被仓库规则（AGENTS.md 的事实优先级）当成高级别事实用——说「这条我抽不出来」是诚实答案，编一个是污染真相源。

每份文档写完，明列缺口，且**按去向分类**：问过但用户也答不上来的 / 还没问的 / 待勘察的。混成一句「有些内容待补充」等于没说——读的人分不出哪些该他答、哪些等你去查。

**没问完的站不算完成。** 每站收尾前自查：这一站的问题清单里，哪几条既不在已有材料里、也没问过用户？有就先问，不要报「第 N 站完成」。

**接手别人写的 draft 也要自查。** 「文档已经存在」不等于「这一站问完了」——你没走过那一站，就不知道它跳过了什么。请用户确认之前先补自查，见下面的开局一节。

| 生成哪份 | 访谈能给 | 必须去勘察 |
|---|---|---|
| requirements.md | 大部分 | — |
| architecture.md | 技术决策、共享机制、集成边界 | 源码盘点、运行环境、Migration Map |
| specification.md | 业务规则、字段、页面、用例 | 现有接口与错误语义 |
| tasks.md | （几乎没有） | 基本全部——要知道代码现状才能拆 |

## 已有文档：抽取的另一个来源

用户手上已经有一份 PRD / 需求文档时，七站大纲照旧适用。**读原文是在「问」之前多了一道来源，不是「问」的替代品**——勘察项一项都不减，该问的也一项都不减。

这句话曾经写成「每一站的『问』变成『读』」，实测的后果：模型读完 PRD 直接报「第 0/1 站完成」，而第 0 站的行业、发展阶段、经营模式、业务规模、当前工具与痛点**一条都没问**——PRD 里没有，于是它们既没进文档，也没进缺口清单，就这么消失了。requirements.md 本来就是「访谈能给大部分」的那一份；原文缺这些，恰恰说明该问。

**这是映射不是搬家**：原文的章节名与 SDD 条款的语义不会一一对应，靠你判断。动手前先完整读一遍（长文档分段读完，不许只读开头），再向用户复述你理解的产品是什么、覆盖哪些章节——理解错了，后面的映射全错。

四条规矩，每条都对应一种真实损坏：

1. **全部落 `status: draft`，一条都不替人确认。** 确认是人的动作，替人确认等于替人签字。
2. **一个字都不许丢。** 映射不进任何条款的内容（落款、修订记录、读不懂的段落）不许悄悄扔掉，**也不许硬塞进条款里凑数**——塞进去的会被下游当成规格用。收尾时原样列给用户，标明它在原文的位置，去向由用户定。
3. **不确定的映射问用户。** 同一段内容既能进 architecture.md 又能进 specification.md 时，给出建议和理由让用户拍板，不要自己悄悄选。
4. **原文没有的，去向只有两个：问用户、去勘察。没有第三个。**
   - **用户脑子里有的就当场问**——公司背景、行业与发展阶段、经营模式、业务规模、现在用什么工具、当前痛点、为什么现在做、本期不做什么。这些 PRD 里常常没有，但用户张口就能答。
   - **依赖代码现状/运行环境的标「待勘察」**，并写清什么时候去勘察。
   - **静默留空不在选项里。** 空条款只有在「问过了，用户也答不上来」时才是诚实的；没问过就留空，用户根本不知道少了什么。编出来当然更不行——会被当成高级别事实用，与总原则那条同源。

收尾报告写五件事：每份文档写了哪些条款；**问过但用户也答不上来的**（这才是诚实的留空）；**还没问的——把问题直接列出来**，不要只写「待补充」；待勘察的以及什么时候勘察；没映射进去的原文内容清单。最后点名下一步该确认哪一份，说一句「建议过一遍」不算交棒。

## 开局：门禁那份文档已经存在时（接手草稿）

开局跑完 `sdd-loop check`，除了「什么都没有」和「一切干净」，还有第三种局面最容易出事：**结构在、check 干净、门禁指向的那份文档已经是 draft，但不是你写的**（上一轮会话留下的、旧版流程产出的、别人映射的）。

**这时不许直接问「确认吗」。** 先做缺口自查，再把选项给用户：

1. 打开那份 draft，对着它落点站的问题清单逐条比——哪些条款有内容、哪些是空的、哪些压根没出现。
2. 空的按去向分类（问用户 / 去勘察），**同上面规矩 4**。
3. 把「还没问的问题」直接列出来，然后再请用户决定。

**`sdd-loop check` 干净 ≠ 这份文档问全了。** check 只对账「声明与事实」——文档在不在、status 对不对、指针悬不悬空。它从不读条款内容，也不该读（那是事后判定，不是本包的活）。所以「check 干净」永远不能当成跳过缺口自查的理由。

**补问是增量的，不是推倒重来。** 给用户的选项里必须有这一条，而且要写清代价：

> ❌ 「不走 PRD 映射，改用一句话需求访谈 → 我从第 0 站重新问」
> ✅ 「第 0 站的公司背景（行业/发展阶段/经营模式/业务规模/当前工具/当前痛点）PRD 里没有、也还没问过 → 我把这 6 个问题补问一遍，答案补进现有草稿，已写好的 REQ-001~021 一条不动」

把补问说成「重新问」，用户以为要作废已有成果，必然选「直接确认」——洞就这么被签进 `confirmed` 了。**在 draft 上补是免费的；签进 confirmed 之后再补，要按仓库文档规则说明原因和影响、重新走确认。** 时机差一步，成本差一个量级。

## 冷启动：仓库里还什么都没有时

`sdd-loop check` 报「还没有 SDD Loop 结构」**不是故障，是新产品的正常起点**——不要把它当错误抛给用户然后停工。（报「判据读不出来」是另一回事：那是文件在但被污染，必须停下请人解决，不许猜。）

**建结构不是本 skill 的活，交给 `sdd-init`**：告诉用户先加载 sdd-init skill（pi 里是 `/sdd init`，Claude Code 等按 skill 名注册命令的宿主里是 `/sdd-init`——**报命令名之前先确认你在哪个宿主，报错的那个用户跑不起来**），由它落地 AGENTS.md、CLAUDE.md、状态文件与 Loop 目录，跑通 `sdd-loop check` 之后再回来从第 0 站开始。`sdd-loop check` 只读，它不会替人建，等它建等不到。

为什么必须先有 AGENTS.md：本 skill 的「抽不出来要明说」之所以是硬约束，正是因为编出来的结论会被 AGENTS.md 的事实优先级当成高级别事实用。那份规则不存在时，访谈产出的文档没有任何东西在管。

结构建好后，阶段文档 `status: draft` 起步，正文由访谈或文档抽取产出，一个字都不许先编。

## 落点约定

阶段文档住在 Loop 目录里（默认 `docs/loops/loop-N/`，以状态文件为准）：requirements.md / architecture.md / specification.md / tasks.md。implementation 由 coding agent 执行；自动化验证之后的架构回写、AI 审查和人工审查包由 `sdd-review` 接管。

**Loop 目录由第 0 站连同 requirements.md 一起建。** 初始化只留 `activeLoop: null` + `nextLoop: N`（空目录进不了 git，提前建会被 check 判成悬空指针）。第 0 站写出 requirements.md 的同时，把状态文件的 `activeLoop` 改成 `N`——目录里有了被跟踪的文件，声明才对得上事实。

**分流仓库里路径多一层**：状态文件是 `docs/loops/<流名>/status.md`，Loop 目录是 `docs/loops/<流名>/loop-N/`，归档是 `docs/archive/<流名>/`。以你所在那条流的状态文件为准，别的流的路径与你无关。

**开一条新流也是第 0 站的活**：新流的 `status.md` 和它首个 Loop 的 requirements.md 在**同一次变更**里建。同一个理由——先建目录、状态文件晚一步，中间那一刻仓库是红的；而只建状态文件不建 requirements，check 会报活跃 Loop 悬空。新流的状态文件照 `activeLoop: 1` 起步（流内编号从 1 开始，不管别的流已经到几了），可以顺手写上 `stream` 和 `owner`——那是给人看的认领信息，工具不判。

编号是锚点：每条条款一个稳定编号，用标题定义（`### BND-002 …`）。**沿用本仓现有编号族**（guide 会列出来），不另起体系，不引入 HTML 注释锚点。

分流不改条款编号：REQ-001、BND-002 这些永远在同一条流的文档族内部互相引用，不存在跨流引用，给每个编号都套上流名是纯噪音。**要带流名的只有 Loop 编号**——正文里提到 Loop 时写 `admin-console/loop-2`，裸写「Loop 2」在分流仓库里有歧义。

## 访谈大纲（七站提问：第 0~6 站，逐站标注落点与勘察项）

### 第 0 站：需求起点与公司背景

问：一句话需求；产品/系统名称；目标模块/业务域；成功标准；行业、发展阶段、经营模式、业务规模；当前工具/系统；当前痛点；一期目标；本期不做。

**这一站几乎全是访谈专属**——公司背景这一组（行业/发展阶段/经营模式/业务规模/当前工具/当前痛点）PRD 里通常写不全，勘察也查不到，只有用户能给。带着已有文档来的也要问，不许因为「原文没有」就跳过。

**开口问之前有两件事，顺序不能反。**

**先确定这一轮属于哪条流。** 开局跑的那次 `sdd-loop check` 已经告诉你这个仓库是单流还是分流（分流时它逐流报，抬头写着有几条流）。单流就跳过这一步。分流就先问用户「这一轮属于哪条流」，答案定下来之后：

- **这条流已经存在**（`docs/loops/<流名>/status.md` 在）→ 读它的状态，按它的 `nextLoop` 编号，别去看别的流的编号。**Loop 编号是流内的，跨流重号正常。**
- **这是一条新流** → 它的状态文件由你在本站连同 requirements.md 一起建（见下面的落点约定）。开新流之前先跟用户确认流名，流名就是范围。

**再读 `docs/backlog.md`**：上一轮开发中记下、当时定了不做的缺陷与新需求都在那儿（仓库门禁规则要求记在那里）。有内容就逐条摆给用户，问「这一轮做不做」——说做的写进本轮需求照常编号，说不做的原样留在 backlog，**不许替用户删**。文件不存在或为空，说一句「backlog 为空」再往下走；**默默跳过等于把上一轮的欠账吞了**，用户根本不会知道有东西没被问。

分流仓库里**只捞本流的条目和标了「跨流」的**——顺序之所以不能反，就在这里：先知道自己在哪条流，才筛得出该摆哪几条。把别的流的欠账也逐条摆一遍是噪音，而噪音会让人开始整段跳过这个环节。

落点：**requirements.md** —— 背景、目标（逐条编号）、非目标（本期不做，逐条编号）、成功标准（必须可测量）。

工程扩展：在 Requirements 逐项判断 Testing、PBT、Security、Resiliency 的风险面；这里只决定适用性和需要追问的事实，不提前写实现方案。没有 PBT 库不等于 PBT 不适用。

勘察：无。

### 第 1 站：业务上下文

问：现行业务流程（现状怎么跑）；参与角色与分工；链路痛点/卡点；一期业务闭环范围；本期业务边界；关键业务决策。

落点：**requirements.md** —— 用户场景（谁/什么情境/做什么/期望什么，逐条编号）、范围。

勘察：无。

### 第 2 站：系统骨架

问：模块划分；核心实体与关系；业务单据；共享机制；技术决策；外部系统与集成边界。

落点：**architecture.md** —— 模块边界、技术决策（每条标明：已确认约束 / 已验证事实 / 候选方案 / 待决问题）、集成边界。同时建立或审查长期 **Architecture Baseline**：先沿用项目已有 `docs/architecture/` 结构；没有时，单系统默认 `docs/architecture/overview.md`，分流默认 `docs/architecture/<stream>.md`。只有真实跨系统关系才新建总体 `overview.md`。

工程扩展：按适用性加载 testing/security/resiliency 规则，写测试边界、信任边界、失败恢复和兼容策略；PBT 只写候选不变量和输入域，不在此阶段选库。

勘察：**这一站访谈给的必须拿勘察核一遍**——源码盘点（真实模块结构和说的是否一致）、运行环境、Migration Map（旧结构 → 新结构，第一列编号）。核不上就标「待勘察」，不许编。写 Baseline 前读 `sdd-init` skill 目录的 `ARCHITECTURE_BASELINE.md.template` 口径；它是内容清单，**不是允许提前创建的空壳**。

### 第 3 站：场景粗流程推演

问：主流程（端到端怎么跑）；关键场景；异常分支；审批流。

落点：**specification.md** —— 主流程与场景、异常分支、审批流。

勘察：现有接口与错误语义——异常分支写得对不对，取决于真实接口怎么报错。

### 第 4 站：字段清单与业务规则

问：核心单据/对象；字段清单（控件、取值、必填、页面归属）；状态机与允许操作；按状态的权限；业务规则。

落点：**specification.md** —— 实体与字段表、状态机、权限矩阵、行为条款。逐类先查口径：`specification.entity-table` / `specification.state-machine` / `specification.permission-matrix` / `specification.behavior`。

勘察：已有数据模型与真实字段约束。

### 第 5 站：用例数据推演

问：样例主数据；样例业务单据；事件序列；测试用例。

落点：**specification.md** —— 用例（数据 + 事件 + 预期）。

工程扩展：把验收条件映射到测试类型；对 Parser、状态机、金额、权限、幂等、排序或并发规则明确 Property、生成输入域和固定示例。若没有有价值的不变量，记录 PBT N/A 的业务理由。

勘察：现有数据形状——样例要长得像真的，不然推演不出真问题。

### 第 6 站：页面规格

问：页面清单；关键交互；校验点/限制；列表/表单/弹窗行为；非功能要求。

落点：**specification.md** —— 页面清单与页面行为（先查 `specification.page-behavior`）；**requirements.md** —— 非功能要求（先查 `requirements.non-functional`）。

勘察：新产品无；有现成页面时勘察现有页面结构。

## 收官：拆任务（**不是提问站**——勘察为主，访谈几乎给不了东西）

七站问完之后还有一件事，但它不靠问。落点：**tasks.md** —— 勘察代码现状后按口径拆（`sdd-loop guide --type tasks.task`）：每条任务写编号、引用的需求/架构/规格编号、完成条件、验证方法。

四项工程扩展产生的测试、负向安全验证、属性生成器、回滚与观测工作必须进入具体任务；不得只在 tasks.md 末尾写一句“补测试”。新增 PBT 依赖属于依赖与供应链变化，必须在 Architecture 和 Tasks 写明并取得用户授权。

不知道现状拆出来的任务是编的——勘察不到就明说拆不了，不许编。

它不计入七站，是因为把它算进「访谈几站」会让人以为还有一轮提问要答，而这一步没有问题可问。**报站数时按七站报，别把它数进去。**

## 不进 SDD 门禁的两件事

访谈过程中常被问起，但它们在本流程里没有文件载体，不要为它们造新文件：

- **原型/视觉稿**走设计工具，不进 SDD 门禁。规格里只写页面**行为**（第 6 站），不写视觉。
- **技术栈、部署、环境约束**如果这轮要定，落 **architecture.md** 的技术决策，标明是「已确认约束」还是「候选方案」。

## 收尾

1. 每份文档 `status: draft` 起步，逐份与用户对齐；用户确认才改 `status: confirmed`。治理模式下随后记录审批并停止，等待下一条 Continue。
2. 明列缺口，按去向分三类：问过但用户答不上来的 / 还没问的（把问题列出来）/ 等勘察的。三类混成一句「待补充」等于没交代。
3. 提醒跑 `sdd-loop check`：状态声明与文件事实是否一致，一跑便知。
